# ADR-004: Использование Java records для DTO

## Контекст

Backend-приложение использует отдельные DTO для HTTP API.

DTO в проекте нужны для того, чтобы:

- отделить внешний API-контракт от JPA-сущностей;
- не отдавать клиенту внутреннюю структуру базы данных;
- принимать только те поля, которыми клиент действительно должен управлять;
- описывать сценарии приложения: регистрацию, создание квиза, подключение к комнате, отправку ответа и получение лидерборда.

Рассматривались два основных варианта:

1. Описывать DTO как обычные Java-классы с Lombok `@Getter` / `@Setter`.
2. Описывать DTO как Java `record`.

Обычные классы удобны, когда объект должен быть изменяемым или когда фреймворку нужны setters. Но для большинства request/response DTO в проекте изменяемость не нужна: объект создаётся из HTTP-запроса или собирается backend'ом для ответа и дальше используется как значение.

## Решение

Использовать Java `record` для основных DTO публичного API.

Примеры таких DTO:

```text
AuthRegisterRequest
AuthLoginRequest
QuizCreateRequest
QuestionCreateRequest
JoinQuizSessionRequest
SubmitAnswerRequest
LeaderboardDTO
```

JPA-сущности остаются обычными классами, потому что Hibernate работает с их жизненным циклом, lazy-связями и изменяемым состоянием.

## Последствия

Положительные последствия:

- DTO становятся короче и проще для чтения.
- API-контракты становятся неизменяемыми после создания объекта.
- Не нужно добавлять Lombok `@Getter` / `@Setter` для простых переносчиков данных.
- Java автоматически генерирует constructor, accessors, `equals`, `hashCode` и `toString`.
- Становится явнее разделение между JPA entity и API DTO.

Ограничения:

- `record` не подходит для JPA-сущностей.
- `record` не стоит использовать там, где объект должен постепенно изменяться через setters.
- Для PATCH-сценариев нужно отдельно решать, как отличать отсутствующее поле от явно переданного `null`.
- При использовании MapStruct нужно учитывать, что records создаются через canonical constructor, а не через setters.

## Правило Использования

В проекте используем такой подход:

- DTO для HTTP request/response описываются как `record`, если им не нужна изменяемость.
- JPA entity описываются как обычные классы.
- Сервисный слой не должен принимать или возвращать JPA entity напрямую через публичные контроллеры.
- Если DTO начинает содержать поведение или сложную lifecycle-логику, его дизайн нужно пересмотреть.
