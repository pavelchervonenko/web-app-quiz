# ADR-005: Публикация полного SessionStateDTO для real-time обновлений

## Контекст

Quiz-сессия меняет состояние во время действий организатора и участников:

- участник подключается к комнате;
- организатор показывает следующий вопрос;
- организатор закрывает текущий вопрос;
- участник отправляет ответ;
- лидерборд меняется;
- сессия завершается.

Frontend должен получать эти изменения в реальном времени через WebSocket/STOMP.

Рассматривались два варианта payload:

1. Публиковать разные события под разные сценарии:
   - `PARTICIPANT_JOINED`;
   - `QUESTION_STARTED`;
   - `ANSWER_SUBMITTED`;
   - `LEADERBOARD_UPDATED`;
   - `SESSION_FINISHED`.
2. После каждого важного изменения публиковать полное текущее состояние сессии через `SessionStateDTO`.

## Решение

Для MVP публиковать полный `SessionStateDTO` в один STOMP topic комнаты:

```text
/topic/sessions/{roomCode}/state
```

REST endpoints остаются источником команд:

- start session;
- join session;
- show next question;
- close current question;
- submit answer;
- finish session.

После успешного изменения состояния backend отправляет новое состояние комнаты подписчикам.

## Причины

Такой подход проще для MVP:

- frontend не должен собирать состояние из разных event payload;
- REST и WebSocket используют один DTO-контракт;
- меньше риска рассинхронизации клиента;
- проще тестировать и отлаживать;
- позже можно добавить более мелкие события, если появится реальная необходимость.

## Последствия

Положительные последствия:

- быстрый запуск real-time режима;
- простая подписка клиента на один topic комнаты;
- единый формат состояния для initial load и real-time updates.

Ограничения:

- каждое событие отправляет больше данных, чем минимально необходимо;
- при росте нагрузки может понадобиться разделить state, question, timer и leaderboard на разные topics;
- для MVP подписка по `roomCode` считается достаточной, но позже нужно усилить WebSocket security.
